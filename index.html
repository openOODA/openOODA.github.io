Why openOODA

Effects. In Rust, Go, Zig, and C the process can open a file or a socket, so the function can too. In openOODA the function holds a token (&FsReadCap, &NetCap, …) or the call does not run. No token, no effect.

Agents. Those languages assume a human will reread the tree. openOODA is built for a short loop: outline, reflect, fix, patch one function. You do not dump the repo into the context.

Secrets. A slipped println ships a key. openOODA marks SECRET fields. Check refuses the sink.

Packages. cargo add and go get fetch with the process’s authority. An openOODA lock is name@version#sha256#CapName. Extra caps refuse.

The path. One everyday path: typecheck, emit C, run. Same source for LLVM, wasm, and x86 when you ask. See the guide.

Safety and security

Tokens. A file, process, or network call takes a capability as an argument. Missing, forged, or zero tokens fail closed. Prefer the small token. Do not take &SysCap when &FsReadCap is enough.

Writes. write_file needs &FsWriteCap and OODA_FS_WRITEDIR. Unset denies the write. Absolute paths and symlinks refuse.

Secrets. Mark a field SECRET. println of that field fails check. A sibling that is not secret is allowed. process_exec is a secret sink.

Packages. A lock line is name@version#sha256#CapName. Path traversal, extra caps, and yank refuse. ooda add --registry checks minisign on the catalog. ooda launch --exec checks that the pin exists after sha, caps, and yank.

Jail. On Linux, &SysCap can apply a Landlock jail and POSIX setrlimit. Empty allowlists and zero quotas fail closed.
