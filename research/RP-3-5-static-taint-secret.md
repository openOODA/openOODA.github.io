## 1. Why this is in DESIGN.md

Section 3 of DESIGN.md says:

> Add the `#[Secret]` tag to sensitive variables (for example, passwords). The compiler tracks the abstract syntax tree (AST) flow. This tracking makes sure that the data cannot go to a function that logs to `stdout` or writes to an unencrypted `&NetCap`.

This is **language-based information-flow control (IFC)** for a practical developer user experience. You mark secrets and the compiler prevents their flow into unsafe destinations (sinks). This feature works with these other features:

- **Capabilities (§3.1):** The authority to write to the network is not the authority to write secrets in cleartext.
- **Narrative diagnostics (§5.5):** The compiler explains the source and sink when it rejects a flow.
- **Zero-trust packages (§5.2):** Libraries must not transmit secrets that they must not see.

Code generated by AI can often incorrectly log request bodies, tokens, and environment variables. Static secret taint stops these errors during compilation.

## 2. Problem statement

### Failure class

| Bug | Example |
|-----|---------|
| Secret to logs | `println(password)` |
| Secret to cleartext network | `fetch(net, url + api_key)` |
| Secret to world-readable file system | `write_file(fs, "/tmp/dbg", token)` |
| Secret through format strings | `"auth=" + secret` into logger |
| Implicit flows | `if secret_bit { log("one") } else { log("zero") }` |

### Users

- Application developers who use credentials, personal data, and session tokens.
- Agent tools that write code for secrets.
- Auditors who require automatic guarantees, not manual searches.

### Primary research question

Can openOODA provide a **usable** mostly-static secret IFC? This IFC must work with capabilities, Backend-C, and ARC. It must also correctly report implicit flows and declassification errors in FFI.

## 3. Related work

### 3.1 Classical IFC languages (academic)

- **JFlow / Jif:** A Java extension with security labels. It features mostly-static IFC and declassification.
- **FlowCaml:** ML with information-flow types.
- **Sabelfeld & Myers (2003) survey:** *Language-Based Information-Flow Security*. This is the primary reference for noninterference and declassification.
- **LIO:** Dynamic IFC in Haskell.
- **JSFlow / FlowFox:** Dynamic IFC for JavaScript.
- **Fabric / Aeolus:** Distributed IFC systems.

### 3.2 Taint analysis in industry

| Tool / system | Style | Notes |
|---------------|-------|-------|
| Perl `-T` / taint mode | Dynamic | Classic, but basic. |
| GitHub CodeQL / Semgrep | Static | Uses patterns to find secrets. |
| Android Lint / R8 | Static | Checks intents. |
| Coverity / commercial SAST | Static | Enterprise rules for secrets and personal data. |
| GraphQL / web frameworks | Mixed | Annotations for sensitive fields. |

### 3.3 Secret-specific product features

- **GitHub secret scanning / gitleaks:** Examines repository content, not data flow.
- **HashiCorp Vault / cloud KMS:** Stores secrets. It does not monitor language flow.
- **Constant-time crypto libraries:** Prevent timing side channels.
- **Swift `SecureBytes`:** Controls memory lifetime, not full IFC.

### 3.4 Capabilities and IFC combinations

- **seL4 information-flow noninterference proofs:** Operating system level.
- **Asbestos / HiStar / Flume:** Operating system IFC.
- Capability systems control *authority*. IFC controls *data*. The DESIGN document requires both. A NetCap without Secret clearance cannot send secrets.

## 4. Design rules for openOODA

### 4.1 Annotation surface

```text
fn login(pw: #[Secret] String, db: &DbCap) -> Result[Session, AuthErr]

fn log_info(msg: String)   // sink: rejects msg if it has Secret taint

fn send_clear(net: &NetCap, body: String)  // cleartext sink
fn send_tls(net: &NetCap, body: #[Secret] String) // approved sink
```

Proposed rules:

1. **Sources:** `#[Secret]` parameters, `env_get` of secret keys, cryptographic private keys, and explicit `secret(x)` calls.
2. **Propagation:** Assignments, arithmetic operations, string operations, and field writes combine taint.
3. **Sinks:** Standard output, logs, cleartext networks, untrusted file system paths, and debug dumps.
4. **Declassification:** Explicit `declassify(secret) -> String` requires an audit capability or the `#[AllowDeclassify]` attribute. Declassification must not be silent.

### 4.2 Capabilities as labeled sinks

`&NetCap` alone is not sufficient. The compiler must use these rules:

- `&NetCap` and cleartext APIs reject Secret data.
- `&NetCap<Tls>` or `send_sealed(net, secret)` accept Secret data.

This unites section 3.1 and section 3.5.

### 4.3 Explicit and implicit flows

| Flow | Handling |
|------|----------|
| Explicit (data dependent assignment) | The compiler must find these. |
| Implicit (branch on secret) | Full noninterference is difficult. The compiler will give a warning or reject secret-influenced arguments to sinks. |
| Timing / termination | Not included in the minimum viable product. We must document this limit. |

**Honesty:** The product must claim **explicit-flow secret safety** only, until we manage implicit flows.

### 4.4 Interactions

| Item | Link |
|------|------|
| 3.1 Capabilities | Capabilities and secrecy control sinks. |
| 3.2 Time/Rand | Side channels. Use RandCap for nonces made from secrets. |
| 3.6 Fuzzer | Make secrets carefully. Do not log test data. |
| 5.5 Narrative diagnostics | Show the path from source to sink. |
| 6.3 FFI | The C boundary is a declassification hole if you do not seal it. |

## 5. Threat and failure model

### What the design prevents

- Accidental logging of secrets and cleartext transmission in pure openOODA code.
- Errors caused by AI tools that print requests for debugging.
- Secret transmission across modules without types.

### What the design does not prevent

| Gap | Notes |
|-----|-------|
| Implicit flows and side channels | Spectre, timing, and termination. |
| FFI and Backend-C writes | Hostile or unchecked C code. |
| Operator declassification errors | Explicit declassification requires review. |
| Secrets in binaries or core dumps | Requires zeroization and operating system rules. |
| Multi-secret lattices | The minimum viable product uses only a Secret or Public boolean value. |

### Failure modes

- **Label creep:** Too many Secret labels make the system difficult to use. We need safe constructors.
- **False confidence:** We must not claim noninterference if we only track explicit flows.
- **Reflection and macros:** AST macros must keep the taint labels.

## 6. Alternatives considered

| Alternative | Decision |
|-------------|----------|
| **Dynamic taint only** | This has runtime cost and misses static agent user experience. It is a useful addition. |
| **Full Jif-style lattices** | This is too complex for the first version. |
| **SAST outside compiler** | Agent loops can easily skip this. We want this in the language. |
| **Vault only** | Storage is not flow. |
| **Encrypt everything always** | This does not stop the logging of plaintext keys. |
| **Depend on capabilities alone** | Capabilities authorize channels. They do not label data. |

**PM.md `3.5`: not-started.**

| Feature | Alpha status |
|---------|-------|

| AST taint propagation | **not-started** |
| Sink refusal | **not-started** |
| Declassify API | **not-started** |

Capability seals control the channel, not the data labels. A program with `&NetCap` can send a password string if it has the capability.

**Do not claim:** "Secret noninterference" or "compiler guarantees passwords never reach stdout".

## 8. Open research questions

1. **Boolean Secret vs multi-level lattice:** What is better for multi-tenant agents?
2. **Opaque secret types vs attributes:** Should we use `Secret[String]` or an attribute on any type? We must balance ergonomics and soundness.
3. **Zeroization on drop:** How does this interact with ARC and temporal memory?
4. **Constant-time mode:** How do we handle cryptographic branches on secrets?
5. **Declassification audit trail:** How do we record this in verifiable packages?
6. **JSON diagnostics:** How do we make a machine-readable flow path for agent automatic fixes?

## 9. Acceptance criteria

### not-started to partial

- [ ] Parse `#[Secret]` on variables and parameters.
- [ ] Propagate explicit flows through assignments and basic operations.
- [ ] Deny Secret data to `println`, logs, and cleartext networks.
- [ ] Make tests pass or fail. Make stable diagnostic code.
- [ ] Document limits for implicit flows and FFI.

### partial to done

- [ ] Track taint across functions with Secret parameters and returns.
- [ ] Use explicit declassification with a capability or attribute. Provide an audit surface.
- [ ] Make a policy table for capabilities and taint (which Net APIs accept Secret).
- [ ] Require declassification or UnsafeFFICap for FFI.
- [ ] Show the narrative diagnostic path from source to sink.
